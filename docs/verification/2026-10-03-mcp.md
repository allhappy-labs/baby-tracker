### Independent-client evidence (why this is not server/client shared-assumption evidence)

- **Go SDK (v1.8.0, this module).** Used for setup, the read/cancel/restart/
  revoked/quota/epoch phases and the raw-socket deadline/busy/concurrency probes.
  This is the same SDK the product composes against, so it alone would not rule out a
  server/client shared misunderstanding of the protocol.
- **Python MCP SDK 1.27.1, direct Streamable HTTP (`python-direct`).** An
  independently maintained client implementation (hash-locked wheels, `--require-hashes
  --no-deps`), driven straight at the server with no Go code in the path. It
  negotiates `2025-11-25`, gets no session ID (stateless), sees the same catalog,
  history, summary and cross-family result as the Go client, and observes the same
  401/429/503 semantics (garbage credential, in-flight concurrency, both global slots
  held) without ever receiving family data on a refusal.
- **Pinned `mcp-proxy` 0.12.0 stdio bridge (`python-bridge`, the Claude Desktop path).**
  The credential launcher execs into the bridge; the bridge exposes a local stdio MCP
  server backed by the real HTTP endpoint. Equal results to Go; an abandoned call is
  cancelled locally without breaking the session; concurrent in-session calls and a
  mid-session 429 are observed and the session recovers afterward; three startup
  failure modes (bad credential, unreachable host, untrusted TLS) never advertise a
  usable tool catalog; six unsafe credential-file shapes are refused by the launcher
  before any network access; EOF, SIGINT and SIGTERM each end the bridge process with
  no leftover child (SIGINT is not guaranteed to be handled by the pinned bridge
  itself — the test accepts "ignored for 10s, then exits on SIGTERM" as the recorded,
  not required, outcome, matching how a desktop host actually closes a child: close
  stdin, then SIGTERM).
- **Codex CLI 0.160.0 app-server, native Streamable HTTP (`python-codex`).** A second,
  unrelated independent client implementation, using the documented
  `http_headers_helper` delivery path (no `bearer_token_env_var`, no literal header, no
  OAuth) in a throwaway `CODEX_HOME`. Tool discovery lists exactly the three tools;
  tool calls match the Go client's results; a mid-session 429 is observed as a bounded
  timeout from Codex's perspective and the next call after it succeeds; a
  never-issued credential gets zero advertised tools and an unspecified (but non-2xx)
  auth status, never a usable catalog.
- **Protocol/version conformance.** The two supported revisions (`2026-07-28`,
  `2025-11-25`) are both exercised; every proof line shows `no_store=all` and the
  stateless surface (no session ID, 405 on GET, 202 on notifications) across every
  client. This is in addition to, not instead of, the SDK-protocol-conformance tests
  already covered in Task 6.

Four separate implementations therefore agree on tool catalog, read results, decimal
exactness, refusal codes and the absence of session state: the composition is not
proven only by the Go SDK talking to its own server.

What the e2e run actually exercised (see [Independent-client evidence](#independent-client-evidence-why-this-is-not-serverclient-shared-assumption-evidence)
above for the detailed results):

- **The Claude Desktop path.** Not Claude.app itself (not installed on this machine),
  but its exact mechanism: the credential launcher (`Server/scripts/mcp-credential-launcher.py`)
  execs into the pinned `mcp-proxy==0.12.0` stdio bridge with `API_ACCESS_TOKEN` in a
  minimal environment, and a Python MCP SDK 1.27.1 stdio client drives that bridge
  exactly as Claude Desktop's stdio transport would. Every documented desktop
  configuration shape (`claude_desktop_config.json`'s `mcpServers` entry calling the
  launcher) was exercised through disposable files in the run's private temp directory,
  never `~/Library/Application Support/Claude`.
- **The Codex / ChatGPT desktop path.** Codex CLI `codex-cli 0.160.0` is installed on
  this machine and was exercised directly: `codex_home()` writes a disposable
  `config.toml` with `http_headers_helper` pointing at the launcher's `codex-headers`
  mode, under a throwaway `CODEX_HOME`/`HOME`/`TMPDIR`, never `~/.codex`. `codex mcp
  list --json` parses the configured server; `codex app-server` initializes, discovers
  exactly the three tools, and calls each one with results equal to the Go client.
  ChatGPT.app (`26.928.21956`, per the prior research note) is installed on this
  machine, but the e2e script drives the Codex CLI's `app-server` directly, not the
  GUI app — the brief's research document explains that the ChatGPT desktop app, Codex
  CLI and IDE extension share the same local MCP configuration for one Codex host, so
  the CLI result is evidence about the shared configuration mechanism, not a
  substitute for clicking through the GUI.

**What this does and does not prove.** It proves the exact configuration shapes
(launcher invocation, bridge argv, `http_headers_helper` delivery) work against a real
disposable server with a real operator-issued credential, through the actual pinned
client software versions. It does **not** prove that Claude.app or the ChatGPT.app GUI,
specifically, accept and use that configuration — neither GUI was driven by this run.
It also does not prove anything about the real deployed Tailscale endpoint, TLS
certificate or ACL — the disposable stack uses a CA-issued leaf certificate
(`openssl`-generated for this run only) at `https://localhost:<port>`, not a Tailscale
certificate.

### Observed non-2xx / `id:null` / concurrent-429 behaviour by client

| Observation | Go SDK | Python direct | Python bridge | Codex |
| --- | --- | --- | --- | --- |
| Garbage/never-issued credential | `error` (connect fails before a usable session) | `HTTPStatusError(401)` | `McpError`, no catalog advertised | zero tools advertised, non-2xx auth status, no `401` string guaranteed in the error text |
| Mid-session concurrency 429 (`id:null`) | refused call surfaces as a client-side call error; session survives | `ClosedResourceError` (session ends) | `McpError`; next call after the window also raced into `McpError` in the committed run — not a hang | surfaced as a bounded `timeout` from Codex's perspective; the **next** call after the window succeeds |
| Global busy 503 (`id:null`) | — (not applicable to this client in this phase) | `ClosedResourceError` (session ends) | not separately distinguished from concurrency in this client's probe | not separately probed |
| Session continuity after a refusal | survives; a fresh session afterward succeeds | a fresh session afterward succeeds | a fresh session afterward succeeds | the next call after the refusal window succeeds |
| TLS/network/auth startup failure | n/a | n/a | never advertises a usable tool catalog | n/a (not probed as a startup failure in this client) |

None of the four clients ever treated a refusal as authorization: no refusal returned
family data, and every client either surfaced an explicit error or ended its session —
never silent success. Where the committed e2e run's own client code treats a specific
outcome as a race rather than a hard requirement (for example, the bridge's
`concurrent_list_call=McpError+McpError` outcome, or Codex's bounded 15-second timeout
on a mid-session 429), that is what the committed assertions accept, not something this
continuation loosened.

## Credential log-scan

The `scan` phase (`Server/scripts/lib/mcp_e2e_client.py scan`) reads every issued
credential's secret bytes in four encodings (raw `btmcp1...` string, raw secret,
standard base64 and hex) and greps every log file the run produced — the app, tls and
db container logs, every client log (`go-*.log`, `python-*.log`, `bridge-stderr.log`,
`codex-stderr.log`) and every file under every throwaway Codex home — for a match.

Result in the HEAD rerun: `python-scan credentials=7 patterns=28 files=5572 codex_home_files=5555 matches=0`.
Seven credentials (go-a, py-a, codex-a, b, epoch2-a, and the two deliberately-invalid
garbage files used to probe refusal paths) × 4 encodings = 28 patterns, zero matches
across every log file produced by the run. This is the same check run4/run5 and every
earlier passing run performed.

## Open acceptance

These remain **explicitly open**, as the brief and the controller's ruling require —
nothing in this task closes them:

- Actual Claude Desktop (the GUI app) accepting the documented `mcpServers`
  configuration and completing a real tool call. Claude.app is not installed on this
  machine.
- Actual ChatGPT desktop app (the GUI) completing a real tool call through its local
  Codex host's MCP configuration. Only the Codex CLI's `app-server` was driven
  directly.
- Desktop-over-Tailscale: a real Tailscale Serve endpoint, its certificate, Host

  identity is a locally generated CA leaf, not a Tailscale certificate.
- Any production grant issuance, deployment, or Unraid rollout.

## Limitations

- The disposable stack's nginx front rewrites `Host` from `$host` to `$http_host` to
  model Tailscale Serve's expected Host-preservation behaviour; this is a modeling
  assumption, not a live measurement of Tailscale Serve itself (see
  [Server/docs/mcp.md](../../Server/docs/mcp.md#56-concrete-rollout-proposal-for-later-separate-approval) for the rollout-time
  check this still requires).
- The soak and e2e stacks both ran on one laptop with other local activity
  uncontrolled; neither is an isolated steady-state measurement.
- The abusive-MCP-traffic ingress-flood limitation documented in
  [2026-10-03-mcp-mixed-load.md](2026-10-03-mcp-mixed-load.md) is unchanged by this
  task: a high-rate connection flood from a well-formed-but-abusive client still needs
  an ingress-level connection/rate limit that this task does not add.
- `go_sdk_unauthorized_connect=error` in the e2e proof line means exactly what it
  says: the Go SDK's own `Connect` treats a rejected `initialize` as a connection
  failure, which is the expected non-2xx client behaviour, not an unexpected crash.
