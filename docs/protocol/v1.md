# Family sync protocol v1

This document freezes the platform-neutral record contract used by the Go
server and future iOS/Android clients. The checked-in examples under
`Server/api/fixtures/v1` are the shared conformance corpus. Defining a
capability here does not advertise it: `/v1/server` lists a capability only
after its owning endpoint is implemented and accepted.

## Identity and negotiation

The server identity is an HTTPS origin with no credentials, path prefix,
query, fragment, or trailing slash. Requests carry
`X-Baby-Tracker-Protocol: v1`. POST bodies repeat `protocol_version` and the
same capability set as the `X-Baby-Tracker-Capabilities` header. Capability
tokens are unique lower-case ASCII values matching
`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`.

The frozen route matrix is:

| Surface | Exact active capability set |
| --- | --- |
| Authentication | `identity-v1`; continuity also uses `device-continuity-v1` |
| Family lifecycle | `family-lifecycle-v1`; recovery uses `recovery-v1` |
| Record sync | `records-v1`; timer batches also use `timer-commands-v1` |
| Full snapshot | `records-v1,snapshot-v1` |
| Import | `records-v1,import-resolver-v1` (exactly both) |
| Live cursor hints | `records-v1,live-hints-v1` and WebSocket subprotocol `baby-tracker.v1` |
| Device push tokens | `push-token-v1` (only on a server with push configured) |
| Live Activity registration | `live-activity-push-v1` (registration only while push is enabled and its worker ready; unregistration always) |

Missing, duplicate, excess, unknown, or known-but-inactive capabilities return
`unsupported_capability`. A missing or mismatched protocol version returns
`unsupported_protocol`. Underscore spellings are never aliases.

### Payload versions

Each entity kind has one current payload version: feed 4, timer 5, sleep 2,
and 1 for every other kind. A `create`, an `update`, and every timer command
must declare exactly the current version for its kind; any other version fails
`invalid_request`, and the whole request is refused before a receipt is
written. A `delete` carries only `baby_id` (`{}` for a baby) and has no
versioned shape, so it is accepted at any version from 1 to the kind's current
version. That rule is permanent: build 2961ca1 declares feed deletes at version
2 and sleep deletes at version 1.

Every entity the server returns (sync pages, snapshots, receipt replays, and
exports generated after migration 000027) is in its kind's current shape,
whatever version wrote it: a feed has
`components` and `feeding_session_id`, a timer has `completed_components`,
`current_bottle_started_at` and `session_id`, and a sleep has
`sleep_session_id`, each session key written even when null. Migration 000027
rewrote stored history into these shapes; no older shape is read or written.
An export archive generated before 000027 keeps the shapes it was written in
until it expires; request a new export for current shapes.

### Feature headers (ignored)

Older clients send `X-Baby-Tracker-Supplements`, `X-Baby-Tracker-Growth`,
`X-Baby-Tracker-Timed-Bottle`, and `X-Baby-Tracker-Feeding-Session` with
`/v1/sync` and `/v1/sync/snapshot`. The server does not read them: a request is
served the same with or without them, and no family's sync or snapshot pages
depend on them. The capabilities that once paired with them (`growth-v1`,
`timed-bottle-v1`, `feeding-session-v1`) are neither advertised nor known.

Pre-redesign apps are unsupported. The server accepts mutations only from the
client built for this protocol revision; an older build's `timer_switch_side`,
`timer_pause`, `timer_attach_bottle`, and `timer_start_bottle` commands are no
longer valid operations and fail `invalid_request`.

## Strict requests and compatible responses

Mutation request objects are closed allowlists at every nesting level. The
decoder rejects duplicate keys, unknown fields, multiple top-level values,
invalid UTF-8 or surrogate escapes, nesting deeper than 16, unsupported
payload versions, non-canonical UUIDs, and non-integer counter spellings before
creating a receipt. Integer IDs, versions, revisions, and sequences are JSON
integers in `0...9007199254740991`; UUIDs are nonzero lower-case hyphenated
values.

Known response kinds decode into typed payloads and ignore additive response
fields. An unknown change kind may be skipped only when its envelope says
`optional:true`; the client advances past that item and requests a new snapshot
if it later enables the capability. An unknown required kind produces
`unsupported_resource`, retains the durable cursor, attempts one authenticated
snapshot, and then requires an upgrade if the kind remains required.

## Canonical values and receipts

Canonical JSON uses UTF-8, lexicographically sorted keys, no insignificant
whitespace, literal Unicode, and no HTML escaping. Required keys are present;
an omitted optional scalar becomes `null`, an omitted optional array becomes
`[]`, and an explicitly null array is invalid. Array order and duplicates are
significant.

Mutation hashes are:

```text
SHA-256("baby-tracker-mutation-v1\0" || canonical mutation JSON)
```

The canonical mutation excludes mutation, account, device, family, and server
IDs but includes entity ID/kind, operation, payload version, observed entity
version, client mutation time, normalized payload, and nullable import ID.
Content hashes use `baby-tracker-content-v1\0` and include entity kind, payload
version, and payload while excluding the mapped `baby_id` relationship and all
server metadata.

Names used for matching follow `nfc-trim-fold-nfc-v1`: NFC, trim the frozen
Unicode 15 White_Space set at both ends, full locale-independent case fold,
then NFC. Display names are trimmed and NFC-normalized without case folding.
Notes and foods are NFC-normalized without trimming. Interior spaces,
diacritics, zero-width characters, order, and duplicates are preserved.

Timestamps accept RFC 3339 offsets no larger than ±14:00 and zero through nine
fractional digits. They normalize to UTC with exactly six fractional digits,
rounding ties to even. Domain timestamps and dates span 1900-01-01 through
2100-12-31. A lexically invalid domain value remains a normalized string in
the semantic hash before domain validation returns `invalid_timestamp`.
`time_zone_id` is a separately validated IANA identifier.

`volume_ml` is an exact finite JSON decimal, never a binary float. It rounds to
six places using ties-to-even, removes trailing zeroes, and normalizes negative
zero to zero. Values from 0 through 2000 are valid after normalization; raw
inputs from -0.0000005 through 2000.0000005 are accepted because the endpoints
round into that semantic range. Bottle volume and contents are either both
non-null or both null.

## Records and commands

The complete payload inventory is represented by the OpenAPI schemas
`BabyPayload`, `FeedPayload`, `SleepPayload`, `DiaperPayload`,
`TimerStartPayload`, `TimerBottleFinishPayload`, `TimerStopPayload`,
`TimerEditPayload`, and `DeletePayload`. Feed `kind` is presentation metadata;
breast intervals and a bottle may coexist. Ordinary record operations are
`create`, complete-replacement `update`, and `delete`. Timer state changes only
through `timer_start`, `timer_finish_bottle`, `timer_stop`, and the timer edit
(`update` on a `timer`). A bottle phase folds into `timer_start`'s
`current_bottle_started_at` instead of a separate begin-bottle command, and a
breast side switch folds into the next `timer_start` (a new one-part timer) or
the timer edit's `components`, instead of a separate switch command.

Successful outcomes are `applied`, `already_applied`, `superseded`, or
`rejected`. An idempotent replay uses `already_applied`, reports the original
status, and returns exactly the original entity, related entities, cursor, and
code. `related_entities` is always an array. A timer stop returns its timer
tombstone as the primary entity and the completed record as a related entity.

Timer commands always address the exact acknowledged timer UUID and repeat its
`baby_id`; commands are never redirected to another live timer. A start wins
only when its baby and kind have no live timer. A losing start is receipted as
`superseded` with the winning timer and allocates no cursor.

A timer edit is `update` on a `timer` entity at `payload_version` 5. Its
`TimerEditPayload` is a patch: `baby_id`, `started_at` (null or omitted leaves
the start unchanged), `components`, which lists only the finished parts that
changed, matched by id and keeping their kind and position, and `session_id`
(required; null clears the link). Because `session_id` is always a real field
of the patch, a session-only edit is content on its own. Rules are judged against the
locked timer at apply time,
in this order: a stopped timer is `superseded/timer_ended` with its
completion; another baby is `record_parent_mismatch`; parts on a sleep timer
are `invalid_timer_kind`; an unknown part id is
`rejected/timer_component_not_found`, a part that changes kind
`invalid_mutation`. A new start more than one minute after or seven days
before acceptance is `invalid_timer_time`. A current side that began at the
old start moves with it; otherwise a start after the current side began is
`invalid_timer_time`. The finished breast seconds must fit between the start
and the current side's start, or acceptance when no side runs, else
`invalid_timer_time`. An edit that changes nothing is an applied, receipted
no-op at the timer's current cursor. Otherwise the timer is changed once,
with one `update` change. Every rejection carries the stored timer. A later stop
completes the timer with the edited values.

Stop is atomic. It validates the requested completion UUID against every live
or tombstoned baby, feed, sleep, diaper, and timer in the family before either
write. A collision is `rejected/completed_record_exists`. A successful stop
tombstones the timer and creates its derived feed or sleep completion as two
changes with consecutive sequences. Later finish-bottle, edit, or stop commands are
`superseded/timer_ended` and return the original completion without changing
it. The timer tombstone remains in snapshots with a null payload.

Only an owner may delete a baby. That command atomically tombstones the baby
and every live record and timer beneath it with consecutive sequences, baby
first, then kind and UUID. It creates no timer completion. The outcome contains
only the baby tombstone and final cursor; clients receive the cascade's
tombstones from the pulls that follow. Any delayed dependent command permanently rejects with
`baby_deleted`. Caregivers may still edit or delete ordinary records, but may
not delete babies.

Import identity policy is immutable per import: `preserve_local_ids` retains
every local baby UUID, while `match_shared` uses the deterministic matching
workflow. Owner conflict choices are `use_existing` with a candidate
`canonical_baby_id`, or `keep_local` with a null canonical ID. The normalization
version is always `nfc-trim-fold-nfc-v1`.

`POST /v1/family/import/resolve` stages contiguous chunks. Chunk zero freezes
the candidate list, mode, normalization version, declared record count, and
initiating device. Later chunks use empty `babies`; empty nonfinal chunks are
invalid. A final chunk must bring the count exactly to its declaration. Chunk
replays return their persisted response even after later chunks or decisions
advance the import. Changed reuse returns `import_chunk_reused`; gaps return
`import_chunk_out_of_order`. Use `GET /v1/family/import/{import_id}` for the
current checkpoint. Same-account sessions/devices can resume; owners may inspect
another member's import and explicitly resolve its conflicts but cannot change
its manifest.

`POST /v1/family/import/{import_id}/resolve-conflict` requires the owner role,
the current resolver revision, a command UUID, and an explicit choice. Decisions
remain separate from mappings. Publication validates the entire exact-match
graph under the ordinary family write lock and commits all mappings and new
babies together. Candidate additions, renames, versions, and deletions invalidate
prior choices with `import_resolution_stale`; refetch status before deciding
again. Occupied local UUIDs with incompatible semantics produce permanent
`baby_uuid_collision`, requiring local repair/export. No alternate UUID is
invented. All three routes require exactly `records-v1,import-resolver-v1` and
`X-Baby-Tracker-Protocol: v1`; JSON bodies carry the same negotiation metadata.

Import GET charges the ordinary device/account sync pull limits. Each import
POST additionally charges one ordinary sync mutation unit for the device,
account, and family. Current family membership and session-family binding are
checked before rate admission. Staging, conflict decisions, receipts, and retained
session markers all consume the family storage quota; quota failures roll back
the entire current transaction. A new ID over either retained history cap returns
nonretryable `import_history_limit`; retries and status of existing IDs remain
available. Incomplete active-session exhaustion returns `import_unfinished_limit`.

Import conflict lists are UUID-ordered and deterministically paged within the
effective sync item/byte envelope. Every resolve or owner-choice response
contains the first page plus `conflict_count`, `conflicts_complete`, and nullable
`next_conflict_page_token`; mapping completion is independent. Status accepts
only an optional strict `page_token`. Tokens are at most 512 bytes, use the page
keyring domain `baby-tracker-import-conflicts-v1`, and bind server instance,
recovery epoch, family/import, viewer account/device/session/security revision,
resolver revision, last conflict UUID, effective limits, expiry, and key ID.
Authentication and authorization precede token lookup. Any conflict, decision,
or visibility change advances the resolver revision, so stale pages fail with
`409 import_resolution_stale` and restart paging.

Every incomplete import expires at its deadline, including finalized ambiguous
imports. Expiry retains the small session-ID row until family purge, always
returns `import_expired` for that ID, and permits bounded cleanup of bulky child
rows. Retained rows count toward the per-family and per-initiating-account
history caps below; the separate unfinished caps remain four/family and one
account globally.

Timer starts are manifest entries with their original timer-start content hash
and mapped baby, and use ordinary timer collision rules. Any other imported
timer command, imported record update/delete, and record-equality
deduplication of timer completions are forbidden. Equal-content record imports
compare the mapped parent separately from the canonical content hash.
Equal records return their current canonical entity and original cursor, persist
that outcome receipt, and change nothing: the family sequence does not advance
and no hint is published. A replay of the
mutation receipt retains that exact outcome even if the canonical row later
changes. Unequal content and tombstones return `record_content_conflict` and
`record_deleted_conflict`, respectively. Imported creates are checked against
their original manifest again under the family lock; they never use last-writer
wins. A published mapping survives baby renames, while a deleted mapped baby
terminates dependent imported writes with `baby_deleted`.

## Live cursor hints and wakes

`GET /v1/live` is an authenticated WebSocket upgrade. It requires a family-
scoped bearer token, exact `v1` protocol metadata, exact
`records-v1,live-hints-v1` capabilities, and subprotocol `baby-tracker.v1`.
An explicitly present `Origin` must byte-equal the canonical origin; native
clients may omit it. Credentials are forbidden in query strings, cookies, and
subprotocol values.

Two refusals of the upgrade are kept exactly as shipped clients have always
received them, and are intentional (`LiveSocket` reads only the status and
`Retry-After`, and always sends a bearer token):

- A request with no `Authorization` header is refused `503
  service_unavailable` (retryable), not `401`.
- A refusal by the per-IP attempt limit is `429 rate_limited` with
  `Retry-After`; its body carries no `server_instance_id` or
  `recovery_epoch`, unlike the device, account and family attempt limits'
  `429`.

Changing either is a wire change.

Each server message is the strict two-field `LiveHint` object from the fixture
corpus. It contains only a family ID and opaque cursor; it never contains an
entity or grants authorization. Hints may be coalesced, reordered, or lost.
Clients always reconcile through ordinary HTTPS sync after a hint and after
every reconnect. Missing `live-hints-v1` support means polling-only operation.

Connections accept no application frames, disable compression, bound inbound
frames to 1024 bytes, ping every 25 seconds, and expire no later than the
access-token deadline or 15 minutes after acceptance. Security changes close
the affected connection, including one authorized just before the change and
not yet established. A commit that advances the family sequence publishes a
hint, after the commit, to the connections this server holds (in process; no
database LISTEN/NOTIFY). Hints are coalesced per family over about 50 ms: a
connection receives at most one hint per family per window, carrying the
newest cursor committed in it. No durable wake intent is recorded in the
write transaction, in either deployment mode. Instead, a background wake
worker records each device's acknowledged cursor (the cursor its sync
request presented) and delivered cursor (the high water of the last final
sync or snapshot page served to it), and compares them with the family
sequence. At most once a minute per device, and once per sequence, it
re-announces the family's high water to devices that are behind, through
their live connections. A re-announced hint may repeat a cursor the
connection already received; clients sync on any hint their local cursor
does not cover. When the server has APNs wakes enabled, a device that is
behind, holds no live connection, and has registered a push token gets no
hint: an APNs background push wakes it instead, at most one every 20
minutes and once per sequence (a change inside that window, or a push
Apple did not deliver, is pushed when the window ends). The push carries
no care data and no family hint (only `{"aps":{"content-available":1}}`);
the app syncs as usual when woken. Only a device that still holds a family
session in that family is pushed. Without APNs wakes, or without a
registered token, a device without a live connection learns of a change at
its next sync.

## Device push tokens (`push-token-v1`)

This is an additive capability, and the one wire addition of the PostgreSQL
authority redesign (owner decision D4): no other route, field or capability is
added. The redesign's ruled behaviour changes on existing routes are:

- A credential whose session row retention has pruned (consumed or revoked,
  kept a day) answers `401 session_revoked`, as any unknown token does,
  where the kept row answered its own refusal.
- A legacy (non-recoverable) refresh checks the session's scope as the
  recoverable path does: a family that is no longer active, or a hosted
  family whose entitlement lapsed, is refused `401 session_revoked`, or `409
  refresh_attempt_conflict` when the only failure of a reused parent is that
  scope.
- A live upgrade whose authorization is revoked after it was read but before
  its socket is bound is closed `1008`, like a revoked connection.
- Live Activity registration (`main`'s routes, ported): on a server with
  Live Activity push disabled, `PUT /v1/live-activities/device` and
  `PUT /v1/live-activities/activity` are not registered and answer a
  plain-text `404` with no JSON body, where `main` answered `503
  service_unavailable`. As with `push-token-v1`, a route the server does not
  serve is absent; a phone registers only while the server advertises
  `live-activity-push-v1`, which it never does with push off. With push
  enabled and the worker not ready they still answer `main`'s `503`.
- On the Live Activity routes the rate limit (`429 rate_limited`) now ranks
  after the request's own refusals (`400`, `409 unsupported_capability`,
  `413`) and family policy, where `main` charged it before the query and
  body checks. This is the request seam's rule, as on `/v1/sync`: those
  refusals are held until the session is authenticated and the charge is
  taken after family policy, so a refused request is never charged.
- `/v1/server` advertises `refresh-recovery-v1` from configuration, also
  while the node is not ready; the recovery routes then answer a retryable
  `503`.
- On the routes that read their body before the credential (`POST /v1/sync`,
  `POST /v1/family/import/resolve` and `…/resolve-conflict`, `PUT` and
  `DELETE /v1/devices/push-token`, `PUT /v1/live-activities/device` and
  `PUT /v1/live-activities/activity`), a request beyond the bound on body
  reads in flight (8 per client address, 64 in all) is refused `503
  server_busy` (`Retry-After: 1`), and an address whose bearers matched no
  session (`401 session_revoked`) 60 times in 10 minutes
  (`BT_RATE_LIMIT_BEARER_FAILURE_IP_COUNT`/`_WINDOW`) is refused `429
  rate_limited` with `Retry-After` until the window ends; both come before
  the body is read, so before every refusal listed for the route. A body
  still unread after 5 seconds, or cut off by a closed connection, ends the
  request before its credential is checked: it answers `503
  service_unavailable` (retryable), as a stalled body did under the earlier
  15-second read timeout, and counts against the same budget. A node at its
  admission limit answers these routes `503 server_busy` after the body is
  read rather than before it.

A server advertises `push-token-v1` in
`/v1/server` only when it has APNs background wakes configured. A server
without push does not register the route (both methods answer `404`) and
does not advertise the capability. Older clients never call it.

`PUT /v1/devices/push-token` stores the APNs device token of the
authenticated session's own device:

- Headers: `Authorization: Bearer <access token>`,
  `X-Baby-Tracker-Protocol: v1` and
  `X-Baby-Tracker-Capabilities: push-token-v1`.
- Body, at most 4 KiB, strict (no other fields):
  `{"protocol_version":"v1","capabilities":["push-token-v1"],"token":"<hex>","environment":"sandbox"}`.
  - `token` is the device token as lowercase hex, even length, 16 to 256
    bytes decoded.
  - `environment` is `sandbox` or `production`, the APNs environment the
    build registered with.
- `204` with no body on success. The device keeps one token: sending the
  same token again, or another one, is also `204` and replaces it.

`DELETE /v1/devices/push-token` forgets the device's token. It takes the same
headers, no body and no query, and answers `204`, also when no token was
stored.

No device ID appears on the wire: the device is always the one the access
token's session belongs to, so a request can never name another account's
device. Any family role may register its phone; the session must be a
refreshed family session of an active family member, as for `/v1/sync`.
The server deletes a token when its device no longer holds an active family
session (sign-out, removal, revocation; checked hourly) and when Apple
reports it unregistered, so a client uploads its token again after it joins
a family or signs in again. The token is never echoed in a response or
logged.

Refusals, in the order the server applies them (the order of `/v1/sync`):

- `503 service_unavailable` when the node is not ready, then the credential
  refusals of `/v1/sync`: no `Authorization` header is `401 access_expired`,
  a malformed bearer token `401 session_revoked`;
- the session's own state: `401 session_revoked`, `access_expired`,
  `epoch_changed` or `reauthentication_required`;
- a session that is not a family session: `403 family_scope_required` (an
  account that never refreshed into its family: `401 access_expired`);
- the request itself, in this order:
  - `PUT`: `400 unsupported_protocol` (the header); `409
    unsupported_capability` for a missing or malformed capability header, or
    one naming a capability the server does not advertise; `400 invalid_request` for a query; `413 body_too_large`; `400
    invalid_request` for a malformed or non-strict body (`400
    unsupported_protocol` for its `protocol_version`); then `409
    unsupported_capability` when the header or body capabilities are not
    exactly `push-token-v1`, judged only after the body decodes (so a
    malformed body with the wrong capabilities is `400`, as on `/v1/sync`);
    then `400 invalid_push_token` (the token or the environment);
  - `DELETE`: `400 unsupported_protocol`, `409 unsupported_capability`
    (header capabilities other than exactly `push-token-v1`), then `400
    invalid_request` for a query or any body;
- family policy, as for `/v1/sync`: `403 membership_revoked`, `403
  entitlement_required`, or a retryable `503`;
- `429 rate_limited` with `Retry-After`, at 10 requests a device or 30 an
  account per hour (`PUT` and `DELETE` together).

## Live Activity registration (`live-activity-push-v1`)

`main`'s Live Activity push wire (`Server/api/openapi.yaml`,
`Server/api/fixtures/live-activity-v1/`), with the two ruled changes listed
above: a plain-text `404` for registration with push disabled, and the
rate limit ranking after the request's own refusals. The routes are served when
`BT_LIVE_ACTIVITY_PUSH_ENABLED=true` and the Live Activity worker is ready;
unregistration is served whether or not push is enabled.

- `PUT /v1/live-activities/device` registers the session's own device for an
  installation: its push-to-start token, APNs environment, payload version,
  feed-break minutes and optional foreground inventory
  (`LiveActivityDeviceRegistration`, `device-registration.json`).
- `PUT /v1/live-activities/activity` registers a running card's update token
  for a baby and kind of the current family (`LiveActivityTokenRegistration`,
  `token-registration.json`).
- Both answer `200` with a `LiveActivityRegistrationReceipt`
  (`registration-receipt.json`): the server instance and recovery epoch, the
  accepted registration (and token) version, the card generations, and any
  unconfirmed push-to-start the device should reconcile.
- `DELETE /v1/live-activities/device/{installation_id}?version=N` revokes the
  installation's registration in the current family at version `N` and
  answers `204`. It has no body; exactly one canonical `version` query
  parameter is accepted. It needs no worker, APNs key or push configuration:
  it succeeds, with the same authentication, authorization and version
  idempotency, on a server whose push is disabled or whose worker is stopped,
  and it alone accepts the `live-activity-push-v1` capability header whether
  or not it is advertised.

Registration needs a refreshed family session of a current member, viewers
included; it conveys no mutation authority. Headers are
`Authorization: Bearer <access token>`, `X-Baby-Tracker-Protocol: v1` and
`X-Baby-Tracker-Capabilities: live-activity-push-v1`; bodies are strict, at
most 16 KiB, and carry exactly that capability. Responses use
`Cache-Control: no-store`. Rate limits are 30 a minute per device and 120 a
minute per account, charged after family policy. (The
`BT_RATE_LIMIT_LIVE_ACTIVITY_DEVICE_*` and `BT_RATE_LIMIT_LIVE_ACTIVITY_ACCOUNT_*`
overrides take effect once the Live Activity worker composition lands;
until then the defaults apply.) Tokens
are never echoed or logged.

Versions are compare-and-set: an identical retry at the stored version is
accepted and changes nothing; a different request at the same or an older
version is `409 live_activity_version_conflict`; an unregistration at version
`N` refuses any later registration at `N` or below. A registration is bound
to the requesting session's lineage: a refresh keeps it; sign-out, removal,
a revoked lineage, or a rejoin (a new lineage) ends it, and the server's
minute authority sweep revokes it. Another account's or device's
installation, a push token another registration holds, a card whose baby ID
is not a baby of the family (an unknown ID or another kind's entity), or a
scope of another family is `403 live_activity_registration_denied`. A card
for a baby since deleted is accepted, as on `main`, so a card still running
for it can report its end.

`GET /v1/server` advertises `live-activity-push-v1` only while push is
enabled, the worker is ready and the node is ready. A server with push
disabled does not register the two `PUT` routes (`404`); with push enabled
and the worker not ready they answer a retryable `503 service_unavailable`.

Refusals, in the order the server applies them (the order of `/v1/sync`):

- `503 service_unavailable` when the node is not ready, then the credential
  refusals of `/v1/sync` (no `Authorization` header `401 access_expired`, a
  malformed bearer `401 session_revoked`), then the session's own state;
- a session that is not a refreshed family session: `401 access_expired`;
- `PUT` with the worker not ready: `503 service_unavailable`;
- the request itself: `400 unsupported_protocol`, `409
  unsupported_capability`, then (`PUT`) `400 invalid_request` for a query,
  `413 body_too_large`, `400 invalid_request` for a malformed body, or
  (`DELETE`) `400 invalid_request` for the version or installation;
- family policy, as for `/v1/sync`: `403 membership_revoked`, `403
  entitlement_required`, or a retryable `503`;
- `429 rate_limited` with `Retry-After`;
- the registration's own answer: `409 live_activity_version_conflict` or
  `403 live_activity_registration_denied`.

## Effective limits

Operators may override these values only inside the listed hard ranges. The
effective values are advertised additively by `/v1/server`; capability
advertisement still remains the authority for whether record sync is active.

Sync mutation limits default to 1,200/device/minute,
2,400/account/minute, and 6,000/family/minute. Sync pull limits default to
120/device/minute and 240/account/minute. Operators may override mutation
counts within 1–100,000 and pull counts within 1–10,000; all five windows are
fixed at one minute. These effective counts are included in `/v1/server`.
The same limit object also reports the fixed concurrency caps: two active
snapshots/account, eight/family, one unfinished import/account, and four/family.

An incremental pull records the family's high-water mark and pages, in
sequence order, the entities changed after the cursor up to it. Pages bound the
exact encoded changes plus sync envelope, excluding only mutation outcomes.
Snapshot pages bound the complete encoded response. Both default to 1 MiB, are
configurable from 64 KiB through 4 MiB, and never split one entity. A mutation
is accepted only when its canonical bytes meet `BT_SYNC_MUTATION_BYTES` and its
resulting entity fits both minimum-size envelopes. Continuations are opaque,
HMAC-authenticated, account/device/session/family/epoch-bound, durable across
restart, and non-consuming. An expired continuation or snapshot token is
`page_expired`; a token whose binding was swept, an hour after it expired, is
`invalid_page_token`. Both mean "take a snapshot" to the client. A
continuation, including a replayed one, returns
the current state of the range it is bound to: an entity changed again since
the first page has moved past the recorded high-water mark and arrives in the
next pull, and a range emptied by such changes ends without a token. A full
snapshot records the family's high-water mark and pages the family's current
rows, tombstones included, in kind and UUID order; it checks the configured
entity and byte caps before its first page and fails atomically. Rows are not
frozen while it pages: a change made meanwhile receives a higher sequence and
arrives in the pull from the snapshot's high-water mark, so the device is
consistent once it has caught up with that following pull.

Latest-state pulls: a pull delivers each changed entity once, in its latest
state, not every intermediate version. An entity created and then edited
between two pulls arrives once, at its last version; a deleted entity arrives
as its tombstone. Tombstones are kept, so a device pulling from an old cursor
still receives every delete.
After create or join changes the authoritative family slot, the account-scoped
session must be refreshed before either sync route is used. Until refresh
persists that exact family binding, sync fails before rate admission or record
writes with an identity-bearing HTTP 401 `access_expired`; clients perform the
ordinary fenced token refresh and retry the unchanged request. A true
`reauthentication_required` response still requires fresh Apple proof.
Import chunks contain at most 1,000 manifests. Names are at most 100 scalars
and 400 UTF-8 bytes; notes 4,096 bytes; foods 100 scalars/400 bytes each and 50
items; side intervals 256 with each and their sum at most 604,800 seconds.
The canonical-record count applies to live feed, sleep, diaper, supplement,
growth-profile and measurement records; baby and timer rows are governed
separately. Charged storage is the sum over the family's stored entities, each
charged its canonical JSON bytes plus 256 bytes, plus 4,096 bytes of deletion
headroom while it is live, plus the family's retained import staging, conflict
decisions and ID markers, plus every mutation receipt the family holds. The
server keeps each entity's latest state only, so an update replaces the
entity's charge, and a delete releases the headroom while the tombstone keeps
its own charge; superseded versions are not stored and not charged. Each
receipt is charged when it is written, applied or not: its outcome's JSON bytes
plus 256 bytes, as an entity row is charged. A receipt replay writes no receipt
and charges nothing, and the server's own import publication writes none. Receipts
are kept 30 days, then deleted and their charge released: a retry within 30
days of its mutation's acceptance replays its receipt.
A mutation is refused, whole, when the family's totals after it and its
receipt would exceed either quota, except an applied deletion that tombstones
its entity: it releases the deletion headroom and remains admissible, receipt
included, so clients can recover space. A deletion that is rejected or changes
nothing releases nothing and is refused over the quota like any other mutation.

A request's family is its session's: the authority reads the session row by
the access token's digest and evaluates family policy from that row. Sync and
snapshot do so in the transaction that serves the request. The live handshake
does so in one statement, with no transaction. The import and export routes
do so in one statement before the route's guarded transaction, which re-reads
the session and evaluates the operation's own policy. No route reads the
caller's family separately.

## Attachments

The beta exposes only the existing attachment metadata contract and a private
`BlobStore` adapter interface. It ships no attachment table, object-store
implementation, upload/download endpoint, transfer URL, quota, or UI.

## Security revisions and account deletion (PostgreSQL authority)

PostgreSQL is the security authority (`docs/operations/security-state.md`).
Two values that clients receive changed meaning with it; neither is parsed by
the shipped iOS client.

- **Export `security_revision` and `audit[].revision`** are the family's audit
  sequence: 1 at family creation, then one more for each security change in
  that family (membership, role, invitation, entitlement, lifecycle and
  integration commands). They used to be node-wide security-ledger revisions.
  Values from archives created before the change are not comparable with new
  ones; treat them as opaque and family-local.
- **`POST /v1/account/delete`** reports `apple_authorization_revocation:
  "manual_required"` in every mode. Hosted mode used to report `pending` and
  revoke the Apple token in a background worker; the hosted credential vault
  and that worker are removed and the Apple refresh token is no longer
  persisted, so revocation is manual until Phase 6 adds hosted Apple
  revocation (open item).

A failed audit chain (`scope_failed` inside the server) reaches clients as a
retryable HTTP 503 `service_unavailable` for that family or account only.
