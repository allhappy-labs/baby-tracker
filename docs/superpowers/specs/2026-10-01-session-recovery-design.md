# Recoverable session refresh design

Date: 2026-10-01. Status: architecture direction and written specification approved by the user on 2026-10-01; subagent-driven execution selected. The implementation plan is approved; task execution and verification are tracked in the investigation document. Companion: [sync performance and live delivery](2026-10-01-sync-performance-design.md). Each specification gets its own implementation plan and review gates; server deployment remains a separate decision.

## Outcome and evidence

An owner or caregiver with an otherwise authorized self-hosted session must not need Apple sign-in merely because a refresh reply was lost, the process stopped during credential installation, or a fenced lease expired after server commit. Preserve 365 days from the original Apple sign-in, ten-minute access credentials, single-use rotation, explicit sign-out, device/membership revocation, recovery epochs and the hosted policy. Recovery does not extend any deadline or resurrect revoked authority. The effective policy deadline uses the existing mode-specific `sessionDeadline`: self-hosted sessions retain the original 365-day ceiling; hosted sessions retain their existing reauthentication/absolute-expiry policy. Recovery also requires the committed child to remain within its frozen refresh expiry. References to a policy deadline below mean these existing limits, not a universal annual lifetime.

The [investigation](../../verification/2026-10-01-sync-reliability.md) records a deterministic failing lost-reply reproduction, the Keychain/SQLite crash window and the measured performance baseline. The deployed auth source has not reverted the annual policy. The earlier owner lineage remains active with a September 2027 deadline. The user confirmed that signing back in restored updates and the second caregiver sees the full history. This supports interrupted owner-side sync; the precise device error/phase that ended the earlier session was not captured. Do not present the reproduction as proof of that incident's exact trigger or claim complete historical-data integrity from the user's observation.

Current legacy refresh treats any uncertain attempt as requiring fresh proof. Clearing that marker or replaying the consumed parent through `/v1/auth/refresh` is unsafe: parent replay can revoke the lineage. Longer lifetimes and shorter polling do not repair this missing recovery seam.

## Chosen approach and alternatives

Add a capability-gated recoverable refresh operation and a resumable client installation checkpoint. Bind every recovery to an unpredictable attempt ID, the parent refresh credential and the existing device-continuity proof. Commit a receipt with rotation, then return the same child credentials on an exact retry. Only a successful durable install acknowledges the receipt.

Use **frozen deterministic derivation inputs**, rather than storing raw token responses or introducing an encryption keyring. The server already derives child credentials using a secret parent-token key and frozen scope, deadlines and security-head values. Extend this under new v3 domains with the attempt/origin/device-binding inputs. A database copy cannot reconstruct credentials without the configured derivation key. Do not recompute against today's head/time.

Keeping legacy uncertainty and just improving its error copy is smaller but still forces sign-in after an interruption. A broad replay grace period allows ambiguity or stolen-token replay to bypass existing protection. Replacing the auth system is a larger migration unsupported by the diagnosis. The chosen approach keeps the existing authority/receipt/fence model and adds a precise recovery path.

## Protocol and compatibility

Advertise `refresh-recovery-v1` only when its migration, configuration, recovery functions and key-retention checks are ready. Add it to protocol definitions, server-info schema, fixtures and client capability parsing. Existing `/v1/auth/refresh`, its v2 token derivation, legacy fixtures and strict request contract remain unchanged.

New `POST /v1/auth/refresh-recoverable` accepts strict v1 JSON: `protocol_version`, exactly `identity-v1` and `refresh-recovery-v1` in `capabilities`, `refresh_token`, canonical lowercase UUID `refresh_attempt_id`, and `device_continuity` with existing `device_id` and `credential`. Reject unknown fields, malformed/zero IDs, extra capabilities and oversized requests before rotation. Use the existing auth request body limit and refresh IP/account/device quotas. Charge valid attempts before rotation; rejected quotas cannot consume credentials. Add a dedicated recovery subject/quota resolver: for a consumed parent, validate the device proof, authority-bound committed receipt and current child authority before deriving its account/device quota subject. Do not reuse or relax legacy `ResolveRefreshSubject`, and never invoke legacy parent-reuse handling merely to classify a recovery request. An unconsumed parent still requires current parent authority before first rotation. Device proof by itself cannot mint authority.

Return the existing session response plus `refresh_attempt_id`, which must equal the submitted attempt. Response credentials, device ID, epoch and frozen deadlines are stable on recovery; account/family presentation is rebuilt from current authorized state. No parent/child session IDs or raw receipt internals need to be exposed publicly. Recovery may return an access token that has already expired; this is a successful recovery of the child, followed by a new refresh of that child's token, not a reason for Apple proof.

New `POST /v1/auth/refresh-ack` requires an authenticated current access credential, `identity-v1` and `refresh-recovery-v1`, `refresh_attempt_id` and the same device-continuity proof. It is an account/device-scoped operation, not a family write. Independently validate the caller's active authority and device-continuity proof. If a receipt exists, require the receipt's device/account/instance/epoch and the same lineage as its child; an active descendant may acknowledge after that child was consumed. If no receipt exists, return 204 without disclosing or deleting anything, after that independent caller/device validation. Do not claim historical lineage validation for an absent receipt or retain permanent tombstones solely for acknowledgement. Wrong proof/device/lineage for an existing receipt is refused without deleting it. Failed acknowledgement never changes ordinary-sync authority or requires fresh proof by itself. If access expired, renew first or retry later.

Stable recovery outcomes: existing terminal auth codes retain their meaning; `refresh_attempt_conflict` identifies a bound parent used with another attempt, `refresh_receipt_unavailable` identifies an exact recovery whose receipt was removed or is no longer recoverable. Distinguish these from retryable transport/readiness failures. A missing acknowledged receipt is not itself a new parent-reuse revocation. Genuine different-attempt replay with valid matching device proof retains the existing reuse-revocation behavior. Invalid device proof must not trigger a destructive reuse action.

An upgraded client probes the confirmed server before choosing the mode for a new refresh attempt, checking canonical origin, instance and epoch. Persist that mode with the attempt. A pending recoverable attempt never falls back to legacy refresh because a probe fails or a server is temporarily downgraded. Report retry/update-required status while preserving the realm. A server without the capability continues through the legacy path. A pre-upgrade uncertain legacy attempt has no server receipt and cannot be retroactively recovered; its existing fresh-proof requirement remains. A valid current session with its stored nonempty continuity proof upgrades at its next renewal without forcing a new sign-in. If a historical Keychain record lacks that proof, preserve the valid session on legacy renewal and record `recovery_unavailable_missing_device_binding`; a later voluntary fresh Apple proof enables recovery. Do not regenerate device authority from a bare session or force sign-in merely to activate the new feature.

## Server state and atomicity

Add migration `000025_refresh_recovery.sql` after immutable migrations 23 (timer pause) and 24 (Growth), assuming no intervening committed migration on integration. Never rewrite an applied migration. Current combined source compatibility becomes exactly 25; migration/grant/digest/schema fixtures and protocol gates must be adjusted together. Performance-only changes introduce no independent schema migration.

A recovery receipt is uniquely bound to instance/epoch/account/device/parent-session/attempt; one parent can have at most one committed recovery child. It stores the exact frozen derivation input and its version, parent digest and key ID, child output key ID and session ID, canonical origin, device-continuity key ID/digest, frozen scope/family/deadlines/security head, created time and original effective deadline. Store no raw access/refresh/device secrets or Apple proof. Retain the child's committed receipt/material commitment so runtime recovery verifies canonical receipt bytes against the authority-committed rotation, not only a mutable row.

Add new `baby-tracker-refresh-*-v3` derivation domains for command/session/access/refresh output, binding the attempt ID, canonical origin and verified continuity key ID/digest in addition to existing v2 fields. Legacy v2 bytes do not change. Reconstruct the same child output from frozen inputs and the named configured key; verify resulting child IDs and token digests against the committed child. Advancing the global head, time or unrelated families never creates another child on recovery.

Preparation stages the canonical recovery material, included in the existing projection-material digest. The authority command commits one rotation. Projection consumes the parent, inserts the child and inserts its receipt in the **same PostgreSQL transaction**. Existing projected stage token fields are cleared; the new durable receipt survives that cleanup. A staged-but-uncommitted request is not a recovery receipt. Projection repair after a committed authority event must reproduce the same child and receipt. Lost replies before commit retry the same attempt without double rotation; lost replies after commit recover the committed output.

Receipt lookup and acknowledgement expose narrow security-definer functions under existing role separation, not broad runtime table grants. Fresh recovery checks the current authority, device binding, epoch, account, membership/entitlement/scope constraints, child status, original effective policy deadline and frozen child refresh expiry under the existing fences. Frozen scope defines derivation only; it is never a current authorization grant. Removed membership, logout, device revocation, epoch change, policy expiry or child refresh expiry overrides a receipt. A consumed child is never made active again. If its consumption is the documented successor of an already completed install, treat that receipt as superseded/acknowledged; an unresolved client with incompatible newer state fails closed and receives an actionable reason.

Delete a predecessor receipt atomically when a committed successor rotation proves possession of that predecessor's child refresh token. Acknowledgement also retires it. This bounds storage when acknowledgement responses are repeatedly lost; don't retain one receipt per ten-minute rotation for an entire year. Unacknowledged genuinely unresolved receipts survive restart and ordinary inactivity until resolution or the earlier of the original effective policy deadline and frozen child refresh expiry. Fresh Apple sign-in with verified continuity may retire older recovery receipts for that device; it must not affect another device's pending attempt. Explicit revocation/epoch expiry and periodic expiry cleanup retire unusable material. Cleanup cannot shorten a recoverable session through an arbitrary short TTL.

Include outstanding receipt derivation/output/device-key references in configuration readiness and key-retirement validation. Normal rotation retains keys required by recoverable receipts and active credentials; removing them must fail validation with key IDs only. Emergency compromised-key removal may intentionally end recovery and must be an explicit operation, not a silent normal-rotation outcome. There is no new secret key introduced by this design.

## Client state machine and crash recovery

Keep the existing account-scoped fenced lease across app/widget/intent renewals. Persist nonsecret recovery/checkpoint fields as additive optional data on the existing `AccountAccessState` model, preserving historical entity identity and old-store migration. Keep `RefreshAttempt`'s legacy decode/default behavior. Keychain `SessionCredentials` gains optional install-binding metadata with backwards-compatible decoding; token material stays in the existing protected Keychain item. No token is written into SQLite, defaults, logs or diagnostics.

| Phase | Durable state | Restart behavior under a new current fence |
| --- | --- | --- |
| Idle | Current Keychain version; no unresolved attempt | Choose supported protocol; generate and persist random attempt ID before send |
| Awaiting result | Parent version, mode, origin/instance/epoch/device and attempt ID in SQLite; parent tokens remain in Keychain | Retry only that recoverable attempt with the same parent and continuity proof |
| Install prepared | SQLite records expected new credential version and SHA-256 token fingerprints before replacing Keychain | Old Keychain: recover the same result and install using the prepared version; exact bound new Keychain: complete SQLite |
| Installed / ack pending | SQLite completion and expected version match atomic Keychain install binding | Allow ordinary sync; acknowledge in the background under current credentials/fence |
| Resolved | Receipt acknowledged or proved superseded; local ack metadata cleared | Continue ordinary renewal |

The install binding includes account/device/origin/instance/epoch, attempt ID, parent credential version, expected new credential version and returned credential fingerprints. Generate the expected version once, persist it before Keychain replacement, and reuse it on a replay. The atomic Keychain item contains both new credentials and that binding. Final SQLite completion updates its version and clears uncertainty while marking acknowledgement pending. An arbitrary changed version is never enough to clear the old marker.

Restart reacquires a new lease; it does not require the generation of an expired pre-crash lease. Check the current account gate, active realm and exact logical attempt/binding before every install/completion. A newer sign-in, different device, changed epoch, mismatched response/binding or stale fence cannot overwrite credentials. Temporary Keychain unavailability preserves state for retry. Irreconcilable mismatch fails closed with a sanitized reason and a visible recovery action; preserve local records.

Only one unresolved refresh attempt exists for an account/device at a time. Acknowledgement retries are durable, coalesced and bounded with backoff; they never block normal mutation/pull work. A successful successor rotation retires the predecessor server receipt even if its acknowledgement reply was lost. Clear superseded local acknowledgement metadata only after observing that committed successor. Fresh Apple sign-in explicitly replaces pending state under its existing fence rules. Promotion from account to family does not silently erase an unresolved attempt.

Unknown refresh errors retain the logical attempt and retry through the recoverable protocol. They never clear a consumed-parent ambiguity or send that parent through legacy refresh. Keep the existing legacy proven-unsent and exact 429/rate_limited safety behavior. Terminal current revocation and policy/refresh expiry still require the appropriate fresh proof/recovery UI.

## Visible status and private diagnostics

Show a persistent actionable family-sync status on Home when fresh Apple proof is required: reuse the localized `Sign in again to keep syncing` message and `Sign in with Apple` action. State that queued entries remain on this phone until syncing resumes; retain those entries. Return the user to the same family after successful sign-in. Do not require visiting Family Settings to discover the writer is unable to send.

Distinguish successful server synchronization, outstanding local deliveries, interrupted renewal, offline retry and a terminal sign-in requirement. A completed empty pull on the second caregiver's phone cannot establish that the owner's local writes were delivered. Do not manufacture a whole-family success guarantee from one phone's last successful request. Use existing server status semantics and derive pending delivery from the store.

Diagnostics contain only bounded phase/reason/status/duration/retry counters and ephemeral correlation values. No access/refresh/device tokens, Apple proofs, names, care payloads, persistent account/family/device identifiers, URLs with secrets or raw production logs. Record `awaiting_reply`, `install_prepared`, `install_completed`, `ack_pending`, legacy fallback, terminal policy reason and live-channel state. Exporting device data or inspecting production logs is not authorized by this spec.

## Verification and acceptance

Strengthen the existing RED fixture into actual server/client protocol tests that assert the same child is recovered and installed and a later ordinary sync succeeds. A test that only avoids a sign-in error is insufficient. Cover:

- Reply loss before server commit, after commit, after projection and after response decoding; exact retries produce one child and no reuse revocation.
- Process death before Keychain save, after its atomic replacement, before SQLite completion and before/after acknowledgement. Relaunch completes safely without Apple proof.
- Lease expiry during exchange, app/widget/intent concurrency, fresh sign-in racing stale refresh, promotion, temporary locked Keychain and divergent install metadata.
- A recovered expired access token triggers a new child refresh; self-hosted annual expiry remains fixed at the original sign-in and is never extended by replay. Hosted policy deadlines and child refresh expiry are likewise preserved, including recovery after parent expiry when the committed child remains valid.
- Wrong attempt/device/parent/proof/origin/epoch, replay from another account, changed membership/scope/entitlement, revocation, consumed child and receipt tampering. No cross-account credential disclosure or resurrected authority.
- Server restart, staged-versus-committed material, failed projection and repair, key rotation/retirement, repeated/lost acknowledgement, absent-receipt acknowledgement and successor cleanup. Genuinely pending recovery survives until the earlier applicable policy/child-refresh deadline; acknowledged material does not accumulate per rotation.
- Old app/new server, new app/old server, pre-upgrade legacy uncertain state and downgraded capability while a recoverable attempt is pending. A valid existing session is not forced to sign in simply to upgrade.
- Historical SwiftData/Keychain decoding, persisted outbox preservation and visible Home sign-in action/localized accessibility behavior.

Applicable gates: literal-count `make test`, focused store/refresher/renewer/restore/status tests, full disposable PostgreSQL/race server suite, Go vet/build, schema/role/digest checks, actual two-client protocol E2E and iOS build/affected UI gates. Distinguish simulator/build/install evidence from physical network/lifecycle acceptance. Use opt-in deterministic fault injection with synthetic accounts; no production fault/load tests without a separate decision.
