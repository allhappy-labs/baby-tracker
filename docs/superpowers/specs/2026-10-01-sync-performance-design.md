# Sync performance and live delivery design

Date: 2026-10-01. Status: architecture direction and written specification approved by the user on 2026-10-01; subagent-driven execution selected. The implementation plan is approved; task execution and verification are tracked in the investigation document. This is a design, not an implementation plan or deployment approval.

## Outcome and scope

When both family members have Baby Tracker open on a healthy private connection, a locally saved care entry should appear on the other phone without waiting for a polling interval. The target is **foreground local save to peer durable application p95 below 1 second**. The interval starts when the writer commits its local entry and ends when the peer commits the corresponding journal change and publishes its observable store update. Measure both durable application and visible UI update; do not substitute an HTTP response time for either. The target applies to normal individual care writes with a caught-up journal, valid sessions and an established live socket. Reconnection, offline backlog, initial import, snapshots and background delivery have separate measurements and honest status.

Improve authenticated server request cost and its scaling with unrelated families and aged security history. Preserve durable authority, revocation and recovery guarantees. No throughput or thousands-of-clients readiness claim follows from the small probes already run. Session lifetime and refresh uncertainty are covered by the companion reliability design; this specification changes neither annual policy nor credential rotation semantics.

## Chosen architecture

### Validated immutable authority state

Introduce one authority-state owner behind the existing security service. It holds an immutable decoded state, its exact trusted `Head` (generation, revision, event hash), recovery identity/epoch binding and an integrity inventory for the selected committed files. Authorization consumers receive narrow read-only views; they cannot mutate cached maps or retain a live authorization capability across its fence lease.

Retain the shared/exclusive process and filesystem fences. The shared fence encloses each existing outer authority read/transaction lease. The exclusive fence encloses authority commands and coordinated recovery. Do not hold a newly introduced shared fence across an entire HTTP request, its radio/response lifetime or a whole mutation batch: that would prolong global revocation blocking. Cache proofs can be reused by nested checks **only inside the same already-held lease**. A new outer lease rechecks integrity. No TTL, directory mtime or filesystem watcher constitutes authorization proof.

On cold start, perform the current full chain validation and state reconstruction before publishing a usable cache. Record, for every selected committed candidate, its expected revision, selected filename, event/prior hashes and SHA-256 of the exact canonical disk bytes. Publish only after matching the trusted head and PostgreSQL projection. The cache is an acceleration of verified material, never a second authority root. Cold start, coordinated recovery and an explicit operator deep audit retain complete strict chain/event validation. A background audit may add defense in depth, but never substitutes for the fresh historical-byte integrity pass before authorization.

For an unchanged head, each outer lease must still read bounded bytes for **every selected historical committed file** and compare their raw digests to the previously fully validated canonical bytes. Check the trusted head freshly; reject missing, malformed, oversized, nonregular or symlink-substituted selected files according to the existing store contract. Check recovery identity, projection head and quarantine before granting authority. Equal cryptographic raw digests permit reuse of decoded event/state data without parsing and reconstructing all events again. Remove the current temporary walk-index write and duplicate backward/forward candidate reads only if the retained inventory produces exactly the selected committed chain and existing rejection behavior. Uncommitted candidates remain outside the selected chain as today.

For an advanced head, under a fence verify the retained prefix's current bytes, then strictly parse/hash/link/apply every new committed candidate. Publish the next immutable state only after the complete extension, recovery binding and projection are valid. An external process advancing the head must be visible on the next lease; a cache miss cannot assume the local process was the writer. A lower revision, changed hash at the same revision, incompatible generation, missing prefix, invalid extension or projection disagreement fails closed and invalidates the usable cache. Do not silently rebuild and accept a known rollback. Recovery can replace a cache only through the existing coordinated recovery flow and its explicit trusted-root/epoch rules.

For a local authority command, derive its decision from the current validated immutable state while retaining the exclusive fence, private prepared-command binding, durable candidate/head ordering and projection checks. Construct/publish a successor without mutating any state currently visible to readers. The first version may copy state once per committed authority write; **no full-state clone on ordinary read/auth/sync paths**. This leaves a measurable global-writer cost rather than introducing a persistent-map dependency without evidence.

### Integrity decision and achievable performance

The chosen design preserves detection of historical-file alteration even when the head is unchanged. Its integrity pass remains **O(committed history bytes) per outer lease**. It removes repeated reconstruction, decoding, cloning, duplicated reads and temporary index writes; it does not promise O(1) historical verification.

Checking only head metadata, file stats or a periodic background deep audit would allow same-head corruption to be served from cache until an audit. That changes the present fail-closed guarantee and is **not approved by this specification**. If the preserved integrity pass prevents the target or aged-history matrix from passing, report the result and stop that optimization claim. Choosing delayed historical corruption detection, storage-enforced immutable content or a different independently verified integrity root requires a separate explicit security-contract/storage design decision. A fast benchmark is not evidence that such a tradeoff is acceptable.

### Read-only views and private capabilities

Replace full exported-state clones on read paths with selector methods that return detached account/device/session/family/membership/entitlement/receipt views. Derive authority-only credential-key references once for each newly validated immutable state and expose detached small key-ID sets. Combine them with the companion recovery design's current eligible receipt/session references. Recovery eligibility also depends on original policy and refresh deadlines: the provider supplies the nearest authoritative revalidation boundary and refreshes under the usual fresh valid lease when that boundary is reached, even if the head stays unchanged. Unknown authority or failed lineage lookup retains references conservatively without caching that uncertain recovery result across leases; a failed required candidate query denies readiness. This is eligibility revalidation, not a generic time-based readiness success cache. Do not rescan every historic authority session for each readiness call; every outer lease still verifies all selected historical bytes and fresh identity/head/epoch/projection. Receipt additions are bound to committed authority rotation and therefore head advancement. Receipt retirement must invalidate the corresponding inventory, or conservatively retain its key references until the next validated inventory refresh; a stale cache may block safe key retirement but must never permit removal of a still-required key. Copy any escaping slices, maps or mutable references in the bounded selected result. Internally shared state is never exposed to callbacks as a writable `State`. Prepared commands retain their existing unforgeable private snapshot token, principal/scope/action binding, epoch and head comparison; a public struct containing a head is insufficient. Lease invalidation ends nested borrowing, including late goroutine access. The cache must not turn a stale prepared command into an authorized write.

After a revocation command commits, publish its successor/invalidation before releasing the exclusive fence as required by current behavior. New transactions cannot use pre-revocation authority; active socket invalidations close affected connections promptly. In-flight work retains only the same serialization window the existing fences permit. Quarantine, key-inventory mismatch and projection failures cannot be hidden by a cached success.

### Readiness without an unchecked cached success

Measure the real application readiness path before changing it. Reuse validated authority views within a valid lease for credential inventory and related nested decisions. Preserve fresh persistent recovery identity, trusted head, epoch and projection checks. Role/separation and migration validation stay at their existing fail-closed boundaries initially; optimizing them is permissible only with an explicit reliable invalidation mechanism and adversarial drift tests. A generic time-based readiness cache is outside this design. `/readyz` must continue to reflect outages, schema drift, role delegation changes and projection/recovery failures.

### Family-indexed live delivery

Maintain the existing authoritative lease registry plus a family-to-lease index, updated atomically on reservation binding, release, revocation, expiry and shutdown. `Hub.Publish` selects only the target family's leases under the existing hub mutex and performs bounded writes outside that mutex. Preserve device/account/process quotas, coalesced high-water cursors, access expiry, grant checks and slow-consumer isolation. Index membership is routing metadata, never authorization.

Replace rebuilding all registered families on every PostgreSQL notification with a validated family-membership lookup against the hub index. Decode/validate the notification's instance, epoch, family and cursor before routing; a foreign family cannot create a registration. LISTEN reconnect/resync still obtains a consistent bounded lease snapshot and reauthorizes it. Periodic security sweeps remain; they may use one valid immutable authority view per sweep and bounded lease iteration. Existing invalidation semantics are preserved.

The normal writer commit must schedule durable delivery and emit its cursor hint through the actual observer. The live socket is the foreground signal; a peer pulls and applies the journal using the hint, never applies care data from an untrusted hint payload. Duplicate/missed/coalesced hints remain safe because the cursor/journal is authoritative.

## Live-path diagnosis gate and privacy

Before changing poll or debounce timers, reproduce and instrument: local save → engine enqueue/start → request completion → server commit/observer → socket hint received → peer pull → durable apply → observable update. Distinguish already-connected sockets, initial dialing, reconnect, refused/rate-limited sockets, sign-out, capability mismatch and requests stalled by queued retries. Emit bounded timing/status codes and ephemeral correlation IDs, not tokens, Apple proofs, account/family identifiers or care payloads. Device-local diagnostics must expose whether the family engine is active, socket state and current sync phase, so “Synced” cannot conceal a signed-out writer.

A deterministic composition test must fail if the hint path is disabled and the update arrives only through the 20 second fallback poll. Separately reproduce dropped socket, foreground return and access renewal. Timer changes require evidence identifying scheduler delay as the remaining cause and a documented energy/rate-limit tradeoff; they are not automatically included here.

Foreground target excludes suspended iOS peers. Background execution/APNs is opportunistic and subject to system budgets; opening the app triggers a fresh attempt and socket reconnection. Report background distributions separately, with no promise of instant delivery while suspended.

## Verification and capacity acceptance

Use disposable synthetic databases/families and complete server composition: actual application/recovery/schema/credential readiness, production authority/store adapters, real default limiter, observer and delivery queue, PostgreSQL listener, TLS/proxy websocket upgrades and actual authenticated client sockets. Reuse the app's composition for peer pull/apply. Separate local save/UI time, scheduling, HTTP, server DB/authority, hint transit and peer apply. Do not put production under load without a separate decision.

Capacity matrix: family counts **1, 32, 128**, active request concurrency **1, 16, 64**, and security ledger sizes at least the observed production revision 248 plus **512 and 2,048 committed security events**. Record exact actual sizes; build valid aged histories with real authority transitions in setup and exclude setup from latency. Where concurrency exceeds family count, explicitly label same-family contention and also retain isolated-family cases. Each family has two authenticated foreground sockets; include realistic existing care history, empty pulls, one-record write/peer apply, caught-up reads and a bounded backlog separately. Default quotas remain enabled; measured over-quota refusals are not mislabeled successful throughput.

For each cell, use a warm-up, a bounded 30–60 second steady measurement, a documented operation mix and at least 200 successful observations where attainable. Bound each cell at 2 minutes and the complete diagnostic run at 20 minutes; timeouts, rejected requests, incomplete cells and resource exhaustion are findings, never silently excluded. Record p50/p95/p99, successful QPS, failures/retries/rate limits, pool acquisition, transaction/lock waits, DB connections, CPU, allocations/RSS, bytes and filesystem integrity-pass time. Capture environment/source/build mode and compare the same fixtures against the unchanged baseline. Use a normal build for timings; race runs are separate correctness gates.

For the healthy two-phone foreground path, require p95 <1 second from save to peer durable/observable apply, zero lost or cross-family changes and no auth churn. The capacity matrix is a measured envelope, not a promise that every contention-heavy cell meets the foreground target. Before rollout, publish which cells satisfy the target and choose the supported envelope; cells outside it must show bounded backpressure rather than resource leaks or authorization failure.

Security regressions include same-head byte corruption/deletion/replacement, rollback, external-process append, CAS loss, stale prepared capability, leaked mutable view, concurrent read/write, projection lag, role drift, key mismatch, quarantine, restored epoch, immediate membership/device/session revocation and notification isolation. Tests must run against warmed caches as well as cold paths and preserve existing frozen protocol/schema/security suites. Verify race safety and lock cleanup/cancellation. Existing client unit/protocol and affected iOS UI gates remain applicable; disclose device/simulator test limitations.

## Capacity limits retained

This is not horizontal multi-writer scaling. Self-hosted authority commands still use a global exclusive fence and durable filesystem writes; cache construction/publication and once-per-write copying may bottleneck frequent account/session activity. Ordinary sync holds family-row locks and intentionally serializes competing writes within a family. The integrity pass still grows with total security history. PostgreSQL pool sizing, listener connection reservation, database connection budget, socket quotas and slow consumers constrain the envelope. Configure a bounded total pool budget only from the measured full composition; do not increase pools or socket limits blindly. Sharding, a new hosted authority adapter, compaction/root replacement and thousands-of-client claims are outside scope.

## Integration and rollout boundaries

Written-spec review precedes an implementation plan and chosen execution workflow. Product changes require those approvals. Keep diagnostics opt-in, preserve unrelated dirty work and commit only scoped reviewed files. Local tests or synthetic composition results do not prove the installed phones or deployed server are fixed.

Production upgrade, including deployed schema 22 to the reviewed source schema and client/server compatibility verification, remains a separate concrete deployment decision. Before it, require reviewed source SHA, immutable image identity, backups, migration/compatibility evidence and rollback constraints. After it, verify deployed identity/schema/readiness, socket upgrade and bounded aggregate health. Merging, pushing, installing apps and release readiness each require their applicable user decision; this specification authorizes none of them by itself.
