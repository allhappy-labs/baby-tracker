# Automatic Family Live Activity Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Automatically start, update and end family Live Activities on the user's built-in server without opening the receiving app or adding an in-app setting.

**Architecture:** Authenticated devices register ActivityKit tokens with the pinned server. PostgreSQL records durable invalidations with canonical family changes; a bounded worker projects current authorized state and sends individual APNs pushes. A launch-owned client coordinator reconciles tokens/cards and prevents stale Lock Screen actions.

**Tech Stack:** Swift 6.2, iOS 26, ActivityKit/App Intents, existing SwiftData/App Group coordination, Go, PostgreSQL/pgx, HTTP/2 APNs with ES256 provider authentication.

**Spec:** [Approved design](../specs/2026-10-03-family-live-activity-push-design.md). Read both documents. Status: approved by the user on 2026-10-03; subagent-driven execution selected from the recommended approach. Implementation is tracked in this worktree's `TASKS.md` and SDD ledger.

## Global Constraints

- Automatic behavior on `https://baby-sync.example-tailnet.ts.net`, instance `<instance-uuid>`, gated by confirmed identity, server capability, current membership and iOS authorization. No in-app toggle or opt-in screen.
- Other self-hosted servers retain current behavior and never relay data/tokens to the built-in server. Push availability is independent of `BT_MODE` and Apple sign-in mode.
- No per-second pushes, unrelated UI redesign, public incoming ports, or server-side language model. Only state changes and expiry reconciliation drive sends.
- Reuse `platform=iOS Simulator,id=D17101C9-01EB-488D-AFE1-58E6C089B853`. Stop if missing/incompatible; never create or clone a simulator.
- Preserve unrelated dirty `TASKS.md` and `work/`. Execute in an isolated worktree, update its tracker, use Conventional Commits and stage explicit task paths only. No push/deploy/install or Apple account mutation without the separate rollout decision.
- Scope includes permission revocation, viewer presentation, registration rotation, feeding breaks, mixed/timed feeding, duplicate reconciliation and stale-action protection. Existing bottle Stop saves usual volume and offers “Set amount” later.
- External CI actions, if any are added, must be pinned to immutable SHAs. No new push library is required: use Go's standard crypto/HTTP stack unless a demonstrated gap warrants a reviewed dependency.

## Review Focus

1. Two commits in one second and device/server clock skew must not let a delayed state replace the current card; Tasks 6 and 9 own ordering tests.
2. Push-to-start succeeds but its response or update-token registration is lost; avoid blindly repeating the alert/start, reconcile observed duplicates; Tasks 6 and 8.
3. Refresh rotates the registering HTTP session while the app sleeps; valid lineage remains eligible, logout/revocation/epoch change stops future sends; Tasks 3 and 11.
4. Two devices have different break limits or a session is regrouped/edited; each receives its own correct break without historical-start bursts; Tasks 4 and 9.
5. A card targets an old timer after family switch, viewer demotion or concurrent stop/start; it must not mutate the replacement timer; Tasks 10 and 11.
